# Releasing — PurpleOTel Monorepo

Zero-stress release pipeline. One command for everything.

## Quick Use

```bash
# 1. Make your changes, use conventional commits:
git add -A
git commit -m "feat(sdk): add OTLP gRPC exporter"
git commit -m "fix(logger): prevent double-flush on shutdown"
git push

# 2. Release — auto-bumps versions, generates CHANGELOG, commits, tags, pushes:
dart run tool/release.dart --minor

# 3. [Optional] Publish to pub.dev:
dart run tool/release.dart --minor --publish
```

## What It Does

```bash
dart run tool/release.dart --version 1.2.0
```

```
[release] Changed packages: purple_otel_sdk, purple_logger
[release] Bumping versions to 1.2.0...
[release] Generating changelogs...
[release] Committing changes...
[release] Done!

# What happened:
#   1. Found packages with changes since last git tag
#   2. Bumped versions to 1.2.0 (with melos, updating all dependents)
#   3. Read conventional commits → generated CHANGELOG.md entries
#   4. Committed and created git tags (purple_otel_sdk-v1.2.0, purple_logger-v1.2.0)
#   5. Pushed commits + tags to remote
```

## Options

| Flag | Description |
|------|-------------|
| `--patch` | Bump patch version (0.1.0 → 0.1.1) |
| `--minor` | Bump minor version (0.1.0 → 0.2.0) |
| `--major` | Bump major version (0.1.0 → 1.0.0) |
| `--version 1.2.0` | Use exact version |
| `--dry-run` | Preview without committing |
| `--publish` | Also run `dart pub publish` for each package |

## Publish to pub.dev

Add `--publish` to also publish all changed packages:

```bash
dart run tool/release.dart --version 1.0.0 --publish
```

Before publishing, make sure:
- `dart analyze .` is clean
- `dart test .` passes all tests
- `CHANGELOG.md` is up to date (auto-generated by the script)
- `pubspec.yaml` has `repository`, `homepage`, `topics` set

## How It Handles Dependencies

The script uses **Melos** under the hood. When publishing packages that depend on each other:

1. **During release**: path deps → version deps (`path: ../sibling` → `^1.0.0`)
2. **After publish**: version deps → path deps (`^1.0.0` → `path: ../sibling`)

This means pub.dev gets valid pubspecs with version constraints, and your local dev environment keeps fast path-based resolution.

## Conventional Commits

Use these prefixes for your commits — the CHANGELOG generator categorizes them automatically:

| Prefix | Category |
|--------|----------|
| `feat:` | Features |
| `feat(sdk):` | Features (scoped) |
| `fix:` | Bug Fixes |
| `fix(logger):` | Bug Fixes (scoped) |
| `docs:` | Documentation |
| `perf:` | Performance |
| `refactor:` | Refactoring |
| `chore:` | Chores (not included in changelog) |

```bash
git commit -m "feat(sdk): add OTLP gRPC exporter"
git commit -m "fix: prevent double-flush on shutdown"
git commit -m "docs: add production deployment guide"
git commit -m "perf(sdk): use Int64List for histogram buckets"
```
